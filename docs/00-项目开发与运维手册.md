## 1. 系统与目录

AI 门道是一个 AI 知识平台，包含资讯、模型目录、工具、知识与实践教程、应用场景、词元/费用计算和管理后台。当前是前后端分离的 SPA，不使用 SSR。

- 前端：React 19、Vite 8、React Router 7，浏览器渲染。
- 后端：Node.js 24、Express 5，提供 JSON API、内容管理和 RSS 定时采集。
- 数据库：Node 内置 `node:sqlite`，SQLite 文件持久化，无单独数据库服务。
- 计算器：Web Worker 中使用 js-tiktoken，词表做 SHA-256 校验。文本和本地文件不发送给模型服务；费用是预算估算，不是真实账单。
- 部署：宿主 Nginx 处理 HTTPS，转发到各环境前端 Nginx 容器，再由容器代理 API 到 Node 容器。

请求路径：

```text
浏览器 → ECS Nginx :443
          ├─ /                  → 127.0.0.1:3100 → 生产前端 → 生产 Node :4000
          ├─ /staging/          → 127.0.0.1:3101 → 测试前端 → 测试 Node :4000
          └─ /nl-online         → 保留的旧静态站
生产 Node → production/storage/mendao.sqlite
测试 Node → staging/storage/mendao.sqlite
```

仓库目录：

```text
frontend/src/          页面、路由、组件、管理界面、词元 Worker
frontend/public/      静态资源及词表
backend/src/          HTTP 服务、数据库、鉴权、资讯采集
backend/src/content/  首次建库使用的真实内容种子
backend/storage/      本地运行数据与凭据（Git 忽略）
shared/               类型、CMS 校验、SEO、计算等共享逻辑
data/                 模型快照、覆盖审计、词表清单
scripts/              开发启动、构建、数据同步、部署检查脚本
tests/unit/           单元测试
tests/e2e/            浏览器测试
.github/workflows/    CI 和生产发布工作流
deploy/               Dockerfile、容器 Nginx 及通用部署参考
deploy/ecs/           当前 ECS 的实际部署脚本和配置模板
docs/                 需求、技术、验收与运维资料
```

当前 ECS 使用 `deploy/ecs/compose.yaml`；不要把通用 `deploy/compose.yaml` 当成当前服务器配置直接覆盖。

## 3. 本地开发

在本机项目根目录执行。Node 要求 `>=24 <25`，CI 和镜像固定为 24.19.0。使用 lockfile 安装，避免随意更换依赖版本。

```bash
git clone git@github.com:zmmyrr-ops/token-calculator.git
cd token-calculator
node --version
npm ci --ignore-scripts --no-audit --no-fund
npm run assets
npm run dev
```

已有项目位于 `/Users/rry/Documents/projects/token-calculator`，直接进入即可，不要重复克隆覆盖。`npm run assets` 准备经过清单校验的本地词表。

`npm run dev` 同时启动前端和后端；也可在两个终端运行 `npm run dev:frontend`、`npm run dev:backend`。Vite 将 `/api` 代理给 Node。

首次使用空数据库时导入种子内容，并在未配置管理员密码的非生产环境生成本地初始凭据文件。数据库已有 `seeded` 标志则不再导入。第一次启动后进入后台并修改初始密码。

本地正式构建预览：

```bash
npm run build
npm start
```

`npm start` 是本地预览命令，不是 ECS 的生产启动方式。停止已有开发服务器后再运行，避免 3000/4000 端口冲突。

需要独立测试数据时，在启动前设置 `DATABASE_FILE`、`NEWS_DATA_FILE` 为绝对路径。相对路径按进程工作目录解析；根命令通常通过 npm workspace 在 backend 目录启动后端，默认数据库为 `backend/storage/mendao.sqlite`。

## 4. 配置与凭据

环境变量的作用：

- `NODE_ENV`：容器为 `production`，影响 Cookie Secure、初始管理员密码要求和允许来源。
- `HOST` / `PORT`：API 默认 `127.0.0.1:4000`，容器监听 `0.0.0.0:4000`。
- `DATABASE_FILE`：容器固定 `/app/storage/mendao.sqlite`，由持久卷映射到各自环境。
- `NEWS_DATA_FILE`：旧资讯 JSON 首次导入路径；当前持续存储使用 SQLite。
- `NEWS_POLL_MINUTES`：默认 15，限制在 5–1440 分钟。
- `SITE_URL`：当前 `https://ruming.top`，后台校验要求 origin 完全一致，不带 `/staging` 或末尾 `/`。
- `ICP_NUMBER`：默认 `浙ICP备2023017888号-4`。
- `APP_ENV`：测试设为 `staging`，用于区分后台 Cookie 名。
- `APP_BASE_PATH`：生产空值，测试 `/staging`，用于后台 Cookie 路径。
- `ADMIN_USERNAME`：默认 `admin`；初始化和密码重置时使用。
- `ADMIN_PASSWORD`：仅空库首次创建管理员时使用，长度 12–128；修改它不会更新已有数据库账号。
- `VITE_BASE_PATH`：前端**构建时**配置；测试构建为 `/staging/`，不是容器启动后动态改变。
- `API_PROXY_TARGET`：本地 Vite 的 API 代理地址，默认 `http://127.0.0.1:4000`。

应用没有自动加载仓库根 `.env` 的 dotenv 流程。本地使用 shell 环境变量；ECS 通过 Compose `env_file` 读取 `app.env`。仅执行 `cp deploy/env.example .env` 不会自动改变后端配置。

站点资料及目录基础信息首次导入 `meta.base` 后由数据库提供；修改 `SITE_URL` 或 `ICP_NUMBER` 不会自动改写已有库中的站点元信息。迁域名需同时处理数据库站点资料、运行配置、Nginx、证书和前端链接，不能只改一个变量。

GitHub Actions Secrets：

- `ECS_STAGING_KEY`：测试镜像导入、测试部署权限。
- `ECS_PRODUCTION_KEY`：只允许部署已在该服务器通过测试记录的版本。

两把密钥不同，服务器授权使用 `restrict` 和 forced command。维护用 root SSH 密钥不能放入 Actions。`deploy/ecs/known_hosts` 固定服务器主机公钥；换机后应通过可信渠道核验指纹再更新，不能关闭主机校验绕过错误。

密码、私钥、`app.env`、数据库与备份不可提交 Git。`.gitignore` 和 `.dockerignore` 排除了运行存储和主要敏感配置；上传其他目录文件前仍需检查内容。

## 5. 数据库设计

实现入口：[database.ts](../backend/src/database.ts)。SQLite 启用 `journal_mode=WAL`、外键约束、5 秒 busy timeout；文件权限为 0600。多步写入使用 `BEGIN IMMEDIATE` 事务。当前模型是单个 Node 实例管理一个数据库文件，不使用 ORM 或独立 MySQL/PostgreSQL。

### 5.1 表与字段

`migrations`：`version INTEGER PRIMARY KEY`、`applied_at TEXT NOT NULL`。当前记录版本 1（基础表）、版本 2（埋点表与索引）、版本 3（普通用户与论坛表）。代码使用 `CREATE TABLE IF NOT EXISTS` 初始化，**没有成熟的逐版本 schema 迁移工具**，新增字段不能只依赖改建表语句。

`documents`：

- `kind TEXT`：`knowledge`、`resource`、`scenario`、`model`。
- `id TEXT`：内容 ID；与 kind 构成复合主键。
- `draft TEXT NOT NULL`：草稿 JSON。
- `published TEXT NULL`：线上 JSON，NULL 表示未发布。
- `revision INTEGER NOT NULL DEFAULT 1`：并发版本号。
- `position INTEGER NOT NULL`：排序顺序。
- `updated_at TEXT NOT NULL`：更新时间。

`meta`：`key TEXT PRIMARY KEY`、`value TEXT NOT NULL`，value 保存 JSON。主要键为 `seeded`、`base`、`contentVersion`、`newsState`。`base` 包含站点信息、覆盖范围、模型目录来源和基础版本；`newsState` 包含采集时间及来源状态等资讯元信息。

`history`：`seq INTEGER PRIMARY KEY AUTOINCREMENT`、`kind`、`entity_id`、`action`、`actor`、可空 `payload`、`at`。保存导入、编辑、发布等操作历史。界面历史查询最多返回最近 30 条；没有自动按 30 条删除历史的逻辑。

`admins`：`username TEXT PRIMARY KEY`、`password TEXT NOT NULL`、`must_change INTEGER NOT NULL DEFAULT 1`。password 为 `盐:scrypt摘要`，不是明文。

`sessions`：`token TEXT PRIMARY KEY`、`username TEXT REFERENCES admins(username)`、`expires INTEGER`。token 是会话令牌的 SHA-256 摘要；expires 使用毫秒时间戳。

`login_limits`：`key TEXT PRIMARY KEY`、`attempts INTEGER`、`expires INTEGER`，用于登录尝试限制。

`news_items`：`id TEXT PRIMARY KEY`、`payload TEXT NOT NULL`，保存资讯 JSON；来源同步状态在 `meta.newsState`。当前最多保留 3000 条资讯，保存时在事务内更新集合。

除主键形成的索引外，目前没有额外全文索引。公开列表分页先在 Node 读取已发布数据、筛选后切片，并非 SQL LIMIT/OFFSET 分页。当前规模能减少网络传输，但更大规模应改数据库查询与全文检索。

`analytics_events`：`seq INTEGER PRIMARY KEY AUTOINCREMENT`、唯一 `event_id TEXT`、`name TEXT`、`page TEXT`、`target TEXT`、`at INTEGER`。记录匿名事件，at 为服务器毫秒时间戳。建立 at 及 (name, at) 索引；保留最近 90 天、约 10 万条记录。无 IP、用户标识、搜索词或输入正文。详见 [埋点模块说明](12-匿名埋点与统计后台.md)。

用户与论坛新增表：community_users、community_sessions、forum_posts、forum_replies、community_limits；字段、认证和种子规则见 [用户体系与论坛](13-用户体系与论坛.md)。

### 5.2 草稿、发布与历史

前台只读取 `published`，保存草稿不会立即影响前台。发布和下架会校验内容引用关系，涉及场景、教程、工具的引用不能随意破坏。删除前必须先下架。更新请求带 revision，冲突返回 409，重新加载后合并修改，不应直接覆盖他人的新版本。

历史恢复把旧 payload 恢复为草稿，并非自动重新发布。需要预览并再次发布才影响线上。生产和测试内容不会自动相互同步。

### 5.3 初始资料与后续迁移

`seed()` 只在空库首次运行。编辑 `backend/src/content/` 或运行模型同步脚本后，重新部署不会覆盖已运行数据库中的内容。已有站点应通过 CMS 管理，或者编写经过审核、备份、测试验证的数据迁移，不能通过删除数据库来“更新数据”。

将来修改 schema：新增编号迁移、事务执行、记录版本；先在备份副本与测试环境验证，再发布兼容代码。涉及字段删除或数据变换时，要明确旧镜像是否还能读取新库。当前不能承诺任意旧版本都可以直接回滚。

## 6. 内容与资讯维护

普通内容操作：登录后台 → 选择模型/知识/工具/场景 → 编辑草稿 → 预览 → 发布 → 前台刷新确认。批量导入应使用专门校验流程，不能把外部数据直接写入 JSON 字段绕过 `shared/cms.ts` 校验。

资讯源当前包括量子位、Google AI、NVIDIA、Hugging Face、Microsoft Research；默认每 15 分钟抓取，页面每分钟刷新可见列表。保留原文链接及时间，失败保留历史并展示来源状态。并非秒级推送，也不保证覆盖全网。

`npm run news:sync` 是源码环境的手动同步命令；操作同一个库前先停止自动采集后端，避免两个进程各自维护的资讯集合覆盖。生产镜像没有打包该源码命令，不要直接在容器里运行它。

`npm run catalog:sync` 用于更新来源快照，`npm run catalog:check` 校验模型资料和词表；这些命令不会自动更新已有线上 CMS 数据库。当前仍存在待逐家核验的厂商资料，不应把收录理解为已完整实测。

## 7. 接口与分页

生产前缀 `/api`，测试对外前缀 `/staging/api`。测试前端代理时去除 `/staging` 后转发给后端。

- `GET /api/health/live`：进程存活。
- `GET /api/health/ready`：读取数据库与资讯状态，供部署健康检查。
- `GET /api/v1/bootstrap?path=/models`：按页面提供初始化数据。无 path 时保留旧客户端的完整响应兼容。
- `GET /api/v1/catalog?page=1&pageSize=24`：模型分页，支持 q、provider、access、support。
- `GET /api/v1/catalog/:id`：单个模型。
- `GET /api/v1/search?page=1&pageSize=18`：跨内容搜索，支持 q、type。
- `GET /api/v1/library/tools`、`/api/v1/library/learn`：工具和文章摘要分页，支持 q、category。
- `GET /api/v1/news`：资讯分页，支持搜索、分类和来源筛选。
- `GET /api/v1/news/sources`：来源状态。
- `GET /sitemap.xml`、`/robots.txt`：站点索引辅助。

页码 1–100000，每页 1–100 条，关键词最多 200 字符。模型页面使用 24 条，搜索/工具/文章页面使用 18 条。非法分页参数返回 400，无匹配数据返回空数组和 total=0；模型不存在返回 404。

`catalog` 返回 models、total、page、pageSize；`search/library` 返回 items、total、page、pageSize，library 另含 categories。筛选和翻页写入 URL，可分享和前进/后退。

管理接口统一 `/api/admin`：session、login、logout、password、overview；`documents/:kind` 支持列表和创建；`documents/:kind/:id` 支持读取、保存、删除；其下 publish、unpublish、history、restore 管理发布及历史；`POST /backup` 下载数据库快照。保存主体为 `{data, revision}`，发布/下架带 `{revision}`，恢复带 `{seq, revision}`；创建传实体本身。精确请求结构以 [admin.ts](../backend/src/admin.ts) 和 [cms.ts](../shared/cms.ts) 为准。

管理写请求要求同源 Origin、有效会话，并且已修改初始密码。公开 GET 接口无需管理员登录；测试站仍受 HTTP Basic 保护。

## 8. 测试与构建

项目根目录执行：

```bash
npm run check
npm run build
VITE_BASE_PATH=/staging/ npm run build -w frontend -- --outDir dist-staging
```

`check` 顺序执行类型检查、ESLint、Vitest、模型/词表校验。`build` 先类型检查，再构建前端和后端。

构建产物：

- `frontend/dist/`：生产静态文件。
- `frontend/dist-staging/`：带 `/staging/` 路径的静态文件。
- `backend/dist/server.mjs`：esbuild 打包后的 Node ESM 入口；npm 依赖 external，因此运行仍需生产依赖。

浏览器测试应对构建预览运行。另一个终端保持 `npm start`，然后执行：

```bash
npm run test:e2e
```

本地默认使用 Chrome；CI 安装 Playwright Chromium。完整套件部分管理后台测试固定访问本地 3000，因此不要只改 TEST_URL 就把完整测试套件指向正式站。CI 使用独立临时数据库；不要把生产库接入自动化写入测试。

失败日志见终端，截图/trace 位于 `test-results/`，报告位于 `playwright-report/`。词元计数同时应在生产构建下验证，避免仅凭开发模式 Worker 的表现判断发布结果。

Docker 构建（需要 Docker 的开发机器或 CI）：

```bash
docker build -f deploy/Dockerfile --target frontend -t mendao-frontend:local .
docker build -f deploy/Dockerfile --target backend -t mendao-backend:local .
```

Dockerfile build 阶段安装锁定依赖、准备词表并构建两个前端目录及后端。frontend 镜像使用 Nginx 1.28 Alpine，包含两套静态路径；backend 使用 Node 24.19.0，非 root 用户运行、安装生产依赖、包含数据库就绪健康检查。正式发布必须使用完整 Git SHA 标签，local 标签不能直接通过发布门禁。

## 9. CI/CD 与发布

### 9.1 日常开发到测试

1. 在功能分支修改、验证并提交，经评审合并 main；当前流程允许直接推送 main，但团队协作推荐 PR。
2. PR 触发 CI，执行依赖安装、校验、生产与测试构建、隔离数据库浏览器测试、两个镜像构建。PR 不执行部署。
3. main 推送通过同样验证后，把两个镜像标为本次完整 SHA。
4. GitHub `docker save | gzip` 经 SSH 传入 ECS，由测试专用命令执行 docker load。
5. 服务器获得部署锁，撤销同 SHA 的旧 verified 记录，加载镜像并部署 staging。
6. 测试容器及 HTTP 健康检查通过后，记录两个实际镜像 ID 到 `verified/<SHA>`。

当前没有使用 ACR；镜像直接经 SSH 传输。前端构建包含两个路径，测试转生产不重新构建。工作流并发控制加服务器 flock 避免同时导入/部署。

纯文档修改（docs、README、TODO、ECS README）被 CI paths-ignore 排除；带 `[skip ci]` 的提交也不会产出新镜像。因此发布输入应使用成功部署测试环境的应用 SHA，不一定是 main 当前 HEAD。手动运行 CI 工作流只验证，不会走仅允许 push main 的测试部署步骤。

### 9.2 测试环境验收

先确认 Actions CI 整体成功，再打开测试站。至少检查：首页、资讯、模型筛选及第二页、模型详情、工具/文章搜索、计算器输入和词表、管理后台登录、移动端布局。内容编辑使用测试账号和测试数据库。

verified 文件代表服务器测试环境健康检查通过，并不替代人工业务验收。上线前还应确认来源抓取错误、数据库兼容性和现存备份。

### 9.3 正式发布

1. 打开 GitHub Actions → **Publish production** → **Run workflow**。
2. 分支选择 main，release 填写已验收的 **40 位 SHA**，可从对应 CI 提交页面复制。
3. 工作流使用生产专用密钥执行 `deploy <SHA>`。
4. 服务器核对 verified 记录与当前两个镜像 ID 一致，备份生产库并保存上一次 release.env。
5. 重建生产容器，等待 Docker 与 HTTP 检查，成功写入 deployments.log。
6. 打开正式站实测关键业务，再确认发布记录。

会有短暂重启窗口；本方案不保证零停机。不要在运行时直接覆盖 deploy.sh，也不要仅用 `docker restart` 代替版本发布。生产工作流不替换数据库，后台已发布内容保留。

维护员在 ECS 上的等价命令是 `/opt/mendao/deploy.sh production <完整SHA>`，同样有镜像门禁；日常优先使用 Actions 保留流程日志。不要手工伪造 verified 文件绕过检查。

最近分页版本为 `65f6e9507dfb608a2df2cd50f7b6e7148cd42152`；这只是编写时示例，实时版本以服务器 release.env 和 deployments.log 为准。

## 10. 回滚与故障恢复

应用发布失败且有上一版本配置时，deploy.sh 会恢复上一次 release.env 并尝试启动上一镜像。无上一版本的首次部署失败不等于已恢复正常，应检查容器并处理。若恢复本身失败，需要人工介入。

主动回滚：在 Publish production 中填入以前通过测试且镜像仍保留的 SHA，走同样发布流程。回滚前确认旧程序与当前数据库 schema 兼容。

**应用回滚不会恢复数据库。** 这能避免覆盖上线后的编辑；若错误涉及内容变更，优先用 CMS 历史恢复草稿再发布。只有确认需要丢弃备份之后的数据时才执行整库恢复。

若镜像已被清理，不能直接回滚。重新构建和导入后即使 SHA 相同，也必须重新通过测试环境健康检查和业务验收。生产比较实际镜像 ID，不只比较标签。

## 11. 备份与数据库恢复

### 11.1 日常备份

在 ECS 执行：

```bash
/opt/mendao/backup.sh production
/opt/mendao/backup.sh staging
systemctl status mendao-backup.timer --no-pager
systemctl list-timers mendao-backup.timer
journalctl -u mendao-backup.service -n 50 --no-pager
```

定时任务每天服务器时间 03:30，随机延迟最多 10 分钟，Persistent=true。先备份生产再备份测试。每次使用 SQLite online backup API，并对生成文件运行 integrity_check；保留 14 天。手动和部署前备份同样执行清理策略。

后台“下载备份”生成临时快照，发送后删除临时文件；下载文件由操作者保管，不属于服务器定时保留目录。备份含管理员摘要和会话数据，应当作敏感资产。

WAL 模式运行中不要单独复制 `mendao.sqlite` 当成一致备份；未合并数据可能在 `-wal` 中。当前备份在同一台机器，不能抵御整机或磁盘丢失。OSS 异地备份尚未接入。

### 11.2 整库恢复流程

以下是维护流程，不是可随意执行的日常更新：

1. 明确目标环境和备份时间，确认恢复后会丢失该时间之后的编辑、资讯和账号变更。
2. 停止发版，取得 deploy.lock，并记录当前 release.env 与镜像 SHA。
3. 数据库尚能读取时先运行 backup.sh 保存恢复前状态；损坏时先保全原始文件，勿覆盖。
4. 停止目标环境整个 Compose 项目，确认没有 Node 或手动采集进程写入该库。
5. 使用 SQLite 检查选定备份的 `PRAGMA integrity_check`，结果必须为 ok；在副本上验证 schema 与目标程序版本兼容。
6. 将旧数据库及同名 `-wal`、`-shm` 一起移动到受限权限的隔离目录，保留取证和二次恢复可能。
7. 复制选定快照到目标 `storage/mendao.sqlite`，恢复原文件 UID/GID 和 0600 权限；不要把旧 WAL/SHM 配到新快照旁。
8. 使用原环境 release.env 启动，验证健康接口、后台账号、已发布数量、模型详情及资讯。
9. 备份可能恢复旧密码和旧会话，应按需要重置管理员并撤销旧会话；记录本次恢复时间与快照。

停止和启动命令见下一节的 dc 函数：`dc stop`、`dc up -d --wait --wait-timeout 120`。恢复前可用 `stat -c '%u:%g %a' /opt/mendao/production/storage/mendao.sqlite` 记录权限。不要用 `docker compose down -v` 或删除 storage 代替恢复操作。

建议定期将备份恢复到隔离测试位置做演练；“备份生成成功”不能替代恢复演练，也不能证明业务数据符合期望。

## 12. 管理员维护

生产后台当前用户名 `admin`，密码以管理员最近设置为准，不在仓库记录。本地、测试和生产是独立账号数据。

鉴权使用 HttpOnly、SameSite=Strict Cookie，生产 Secure，正常会话 8 小时。生产名 `mendao_admin`，测试名 `mendao_staging_admin`，Cookie 路径分别 `/api/admin`、`/staging/api/admin`。修改密码会撤销旧会话。

本地源码环境忘记密码，在项目根执行：

```bash
DATABASE_FILE="$PWD/backend/storage/mendao.sqlite" ADMIN_USERNAME=admin npm run admin:reset
```

生成随机临时密码到该数据库旁的 `admin-initial-credentials.txt`，清理旧会话和登录限制，强制首次改密。只在本人终端打开此文件，不贴到工单、日志或聊天。

生产镜像仅打包 server.mjs，不包含 reset-admin 源码和 tsx，因此不能直接运行上述 npm 命令。生产忘记密码时由维护员先备份，在容器内使用与 [reset-admin.ts](../backend/src/reset-admin.ts) 一致的数据库重置过程，或准备专门受控维护版本：生成随机密码、scrypt 哈希、事务更新指定 admins 记录、撤销其 sessions、清理登录限制、将临时凭据写入权限 0600 的私有文件、首次登录改密。不得通过修改 ADMIN_PASSWORD 或把哈希改成明文来重置。

正式站密码重置不应顺手修改测试/本地密码。找不到账号时先检查环境和数据库路径，避免误创建新库。

## 13. 服务器日常操作

以下在 ECS root 或具备相应 sudo/Docker 权限的维护会话执行。先定义目标环境，只作用于一个环境：

```bash
APP_ENV_NAME=production
case "$APP_ENV_NAME" in production|staging) ;; *) exit 1 ;; esac
dc() {
  docker compose -p "mendao-$APP_ENV_NAME" \
    --env-file "/opt/mendao/$APP_ENV_NAME/release.env" \
    -f /opt/mendao/compose.yaml "$@"
}
dc ps
dc logs --tail=100 backend
dc logs --tail=100 frontend
```

查看版本、容量与外网状态：

```bash
sed -n '/^RELEASE_ID=/p' "/opt/mendao/$APP_ENV_NAME/release.env"
tail -20 /opt/mendao/deployments.log
df -h /
free -h
docker system df
docker stats --no-stream
curl --fail --silent --show-error https://ruming.top/api/health/ready
nginx -t
```

只需要重启原版本时 `dc restart backend`；修改 app.env 后必须 `dc up -d --force-recreate --wait --wait-timeout 120 backend` 才会重新应用环境变量。修改配置前先备份，重建后检查健康和日志；不要直接打印完整 app.env。

每环境后端限制 512 MiB / 0.65 CPU，前端 96 MiB / 0.25 CPU。容器日志每文件 10 MB、3 个轮转文件。前端只映射回环 3100/3101；Node 4000 不对公网开放。

镜像清理前，列出生产、测试、上一版本与需要回滚的标签；保留对应镜像。不能执行无差别 `docker system prune -a`，否则可能删掉回滚依赖。备份清理、镜像清理和日志清理是不同事务。

TLS 文件：`/etc/nginx/ssl/www.ruming.top.pem` 和同名 `.key`。编写时证书到期日为 2027-02-13，自动续期尚未确认。检查证书可读取 pem 信息，私钥无需输出。更新证书后先 `nginx -t` 再 `systemctl reload nginx`。

## 14. 基础设施变更与重建

应用 CI **不会自动同步** `/opt/mendao` 的 root 部署脚本、宿主 Nginx 配置或 systemd 单元。仅把 deploy/ecs 文件推送 Git 不代表服务器已经应用。

更新脚本流程：备份当前文件 → 上传新临时文件 → `bash -n` → 等待 `/opt/mendao/deploy.lock` → 同目录原子 mv 替换 → 保持 root 所有权和执行权限 → 验证。曾有直接覆盖运行中脚本导致 shell 解析失败的情况，禁止 scp 原地覆盖执行中的 .sh。

更新宿主 Nginx：保留 `/nl-online`、现有证书、测试认证以及 www 规范域名跳转；备份、校验后 reload。若校验失败还原配置文件，不重启覆盖当前可用进程。bootstrap 的 gzip 压缩目前在宿主精确 location 中，属于宿主配置。

重建或迁移 ECS 的顺序：

1. 准备兼容 x86_64 Linux、磁盘与安全组；公网仅开放所需 HTTP/HTTPS 和受限 SSH。
2. 安装并核验 Docker、Compose、Nginx、curl、flock；按所选发行版官方方法维护系统，不直接复制其他系统包命令。
3. 建立 `/opt/mendao` 目录和环境存储，正确设置容器 Node 用户可写权限。
4. 从受控副本恢复部署脚本、compose、各环境配置、数据库快照、TLS 证书、测试 htpasswd；所有秘密单独交付。
5. 配置两把独立部署公钥的 forced command，核验新主机指纹并更新 known_hosts。
6. 通过 CI 导入镜像并部署测试环境，完成恢复和业务验收，再发布生产。
7. 安装备份 service/timer，daemon-reload 后启用 timer，手动执行一次并检查快照。
8. 验证 Nginx 路由、HTTPS 和数据库后切换 DNS；保留旧环境用于回退。

当前没有包含整机全自动初始化的 Terraform/Ansible 脚本；重建需要上述资源与秘密副本。重建空库与恢复既有站点是两种操作，恢复既有站点优先放置快照，避免意外生成新的初始账号与种子库。

## 15. 排障与维护清单

### “请求来源不被允许”

确认地址为 `https://ruming.top/admin`；www 自动跳转后刷新旧页面。检查 SITE_URL 是否为准确 origin；测试后台使用 `/staging/admin`，但 origin 仍是 `https://ruming.top`。不要用关闭校验或允许任意 Origin 作为修复。

### 首次访问慢

分别查看 JS、bootstrap、列表和图片请求。页面现在按路径初始化，模型按 24 条分页。2026-09-17 实测压缩首页初始化约 15 KB，模型初始化约 2.3 KB，模型第一页约 24 KB；不是整页总资源大小。旧无 path bootstrap 仍返回完整数据，用于兼容。还应检查静态 JS、图片、词表和客户端网络；首次计算需另下载词表。

### 502 / 504 或部署超时

先 dc ps、backend/frontend 日志，再检查对应回环 3100/3101 与数据库目录权限、磁盘、内存。确认后端监听 0.0.0.0:4000。资讯某个源失败不等于整个 API 不可用；应用健康通过也不等于所有境外 RSS 可达。

### 内容修改不显示

确认操作的是生产后台、已经发布而非只保存草稿；刷新页面，检查 published。修改种子代码不覆盖既有库。多管理员冲突先处理 409，不能静默覆盖。

### 测试环境资源 404

检查前端是否以 VITE_BASE_PATH=/staging/ 构建，镜像是否包含 dist-staging，API 路径是否带 `/staging/api`，宿主 location 是否保留。测试访问 401 可能是 HTTP Basic，不一定是后台账号错误。

### 登录失败 / Cookie 丢失

区分 Basic 认证和应用登录；检查 HTTPS、Origin、APP_ENV、APP_BASE_PATH、must_change 及登录限制。修改 app.env 中 ADMIN_PASSWORD 对旧账号无效。恢复旧数据库可能恢复旧密码。

### CI 成功但版本未上线

查看整条工作流和部署步骤，而不只看构建成功。PR、手动 CI、文档提交不会自动部署测试。生产需要 Publish production 单独触发；核对输入 SHA 是有镜像的应用提交。宿主配置还需要维护员另行应用。

### 日常检查

- 每次发布：CI、测试站、数据库备份、正式站关键路径、版本记录。
- 每日或自动告警：服务健康、磁盘、备份任务失败、资讯源状态。
- 每周：备份完整性及抽样恢复、镜像占用、模型资料更新。
- 到期前：证书更新、ECS/域名续费；检查安全组和部署账号权限。

当前文档中的检查频率是维护建议；除已有备份和 RSS 定时任务外，不代表已经部署监控告警或自动巡检。
