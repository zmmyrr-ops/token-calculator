## 1. 已确认决策与假设

- **框架：Next.js App Router + React + TypeScript。** 用户明确偏好 React / Next.js。
- **运行：阿里云 ECS 上自托管 Node.js，使用 Docker + Nginx。** 不依赖 Vercel。
- **渲染：公共页面 SSR，浏览器水合后本地计算。** SSR 不意味着每次键入都发送正文到服务器。
- **首版后端：公共模型目录、方法说明和健康检查。** 不接收用户提示词，不生成回答。
- **首版存储：随版本发布的 JSON 数据，无数据库、无 Redis、无登录。** 偏好仅在浏览器本地。
- **首版推荐：确定性规则，不调用大模型。** 历史统计预测和云端分类为后续独立能力。
- 未确认：ECS 系统、CPU/内存、地域与架构、域名具体值、备案号、站点名称。

部署假设为 Linux 单机；试运行资源参考为 2 vCPU / 4 GiB，需按现有机器压测调整。这不是最低配置承诺，不据此要求购买新服务器。构建在开发机或 CI 的 Linux 容器内完成，避免抢占小规格 ECS 的线上资源。

## 2. SSR 框架选择

### 2.1 Next.js：采用

React 技术栈，App Router 可组合服务端与客户端组件，支持 Node 自托管。适合本项目把可检索的公共内容放到服务端、把输入和分词留在浏览器。需要明确控制渲染和缓存，防止误做成静态壳或缓存私人内容。

### 2.2 Nuxt：可选，未采用

Vue 体系、通用渲染和 Node 部署能力适合类似项目。用户已经选定 React，本项目不引入第二套前端体系。

### 2.3 SvelteKit：可选，未采用

具备 SSR 与独立 Node server 适配器。工具站可以使用，但相对于用户现有偏好没有切换收益。

结论：**只使用一个 SSR 框架 Next.js**；三个候选是选型比较，不是混合技术栈。参考：[Next.js 自托管](https://nextjs.org/docs/app/guides/self-hosting)、[Nuxt 渲染模式](https://nuxt.com/docs/4.x/guide/concepts/rendering)、[SvelteKit Node 适配器](https://svelte.dev/docs/kit/adapter-node)。

## 3. 技术栈与项目结构

推荐依赖：Next.js 当前受支持稳定版（本次查询官方文档为 16.x）、其兼容 React、TypeScript strict、Tailwind CSS、Zod、decimal.js、js-tiktoken、Vitest、Playwright。Node 使用实施时与 Next.js 兼容的受支持 LTS；精确版本在初始化时写入运行时版本文件、Dockerfile 和锁文件，不能生产运行时安装 `latest`。

## 4. SSR 与浏览器计算的边界

### 4.1 首次请求

浏览器 → DNS → ECS Nginx HTTPS → Next.js Node → 校验过的公共目录快照 → 完整首屏 HTML → 水合交互 → Web Worker 分词。

首页、`/models`、模型详情在请求时渲染。服务端输出标题、表单标签、模型与方法信息，不含私人文本。公共目录以相同版本传给客户端，避免水合时价格变动产生不一致。

可用当前 Next.js 的 `connection()` 显式使页面以下内容在请求时渲染，见[官方说明](https://nextjs.org/docs/app/api-reference/functions/connection)。示意：

```tsx
import { connection } from 'next/server';
import { loadPublicCatalog } from '@/lib/catalog/load.server';
import { Calculator } from '@/components/calculator/Calculator';

export default async function Page() {
  await connection();
  const catalog = await loadPublicCatalog();
  return <main>
    <h1>词元计算器</h1>
    <p>计算输入用量，比较模型成本。</p>
    <Calculator initialCatalog={catalog} />
  </main>;
}
```

`Calculator` 为客户端组件，但其初始表单仍参与服务端预渲染。Worker、FileReader、localStorage 只在客户端生命周期中初始化。不能把整个页面设为仅客户端动态导入。具体 API 用法以锁定版本验证为准。

### 4.2 缓存

- 公共页面首版不在 Nginx/CDN 做整页缓存，避免 RSC 响应与 HTML 被错误混用；Next.js 公共数据可在进程中读取固定发布快照。
- 哈希 JS/CSS/词表长缓存并 `immutable`；非哈希资源短缓存。
- `/api/v1/catalog` 使用 ETag 和短公共缓存，包含 snapshotVersion；打开的计算器保持当前快照，用户点击更新后统一重算。
- 未来包含正文的请求必须 POST + `Cache-Control: no-store`，不得放入共享缓存或 URL。

## 5. 分词计算内核（R01、R02）

### 5.1 适配器和准确性分级

统一接口 `count(text, tokenizerSpec) -> CountResult`。

```ts
type CountResult = {
  status: 'ok' | 'estimated' | 'unavailable';
  scope: 'text-only';
  count: number | null;
  range: { low: number; high: number } | null;
  tokenizerId: string | null;
  tokenizerRevision: string | null;
  modelMapping: 'verified' | 'reference-only' | 'unknown';
  reasonCodes: string[];
};
```

- **固定编码**：js-tiktoken 加载已固定版本词表，对当前字符串计数。库支持什么编码与具体 API 模型使用什么编码是两件事；分别核验。
- **其他模型**：使用厂商公布的 tokenizer 文件，在验证兼容的浏览器适配器中加载；必要时评估 Hugging Face 的 tokenizer 实现，但不要仅为计数打包整个推理运行时。
- **未知映射**：可由用户选择参考编码，结果必须为 `reference-only`；没有可靠关系时模型输入数为 unavailable。
- **经验估算**：只有存在版本化的语言/文本类别系数和误差样本时才能启用。中文字符乘常数不作为精确计数；无系数就不显示数值估算。

js-tiktoken 是第三方 JS 实现，不能称为厂商官方计数接口；参考其[维护仓库](https://github.com/dqbd/tiktoken)。DeepSeek 的[官方说明](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)提供离线资源，但生产 API 模型与该资源版本的对应关系仍需核验。

### 5.2 Worker 处理流程

1. 输入按实际字符串保留；用 TextEncoder 计算 UTF-8 大小并检查 1 MiB 限制。
2. 防抖 250ms；每次提交递增 requestId。中文输入法 composition 结束再提交。
3. 按不同 tokenizer 去重，最多并行处理 6 个候选中的实际编码集合。
4. Worker 懒加载词表并校验资产版本；缓存最多两个大型词表，超过时按 LRU 淘汰。
5. 回传带 requestId 的结果；UI 只接受最新结果。超时 5 秒提示等待/取消；终止 Worker 是真正中断，不能只忽略结果后任其无限消耗。
6. Worker 崩溃可重新启动；不得静默把原文上传服务器。大文本不降级到主线程长时间计算。

特殊处理：空格不 trim；换行对应文本框实际值；字符数使用 Unicode code point 口径并说明不是字形数；emoji、组合字符和特殊 token 字面量作为普通用户文本编码。不要把看起来像 special token 的字符串当成保留控制符。

### 5.3 上下文容量

正文计数与真实请求输入分开。已知历史输入可手动补充，未知系统/工具封装明确标记遗漏。检查每个模型的 contextWindow、maxOutput、推理共享输出预算规则；约束含义按模型元数据定义。

若任一情景超限，标记该情景不可行；不要悄悄截断预算后再推荐。对历史或模板未知的情况，只能提示“基于已知输入检查”，不能声称请求一定能放入窗口。

## 6. 模型、价格与来源数据（R06）

P0 以人工核验后提交的数据快照为事实源。价格不得由分类模型生成。更新程序只校验格式和提醒复核，首版不自动爬网页后直接发布。

目录覆盖范围按需求第 3.1.1～3.1.3 节执行，不设三个厂商或 6 个型号的总量限制。每个具体可选渠道记录至少包含：

```ts
type ModelSpec = {
  id: string;                 // 产品内唯一 id，包含渠道/地域/版本
  canonicalModelId: string;   // 独立型号，跨渠道/别名去重统计
  familyId: string;
  aliases: string[];
  manufacturer: string;
  provider: string;
  apiModelId: string | null;  // 网页专属或权重模型可没有 API ID
  displayName: string;
  channel: string;
  region: string;
  availability: 'active' | 'deprecated' | 'unverified';
  accessType: 'api' | 'web-only' | 'weights' | 'restricted';
  releaseStage: 'stable' | 'preview' | 'retired' | 'unverified';
  tier: 'mid' | 'high' | 'frontier' | 'economy' | 'unverified';
  catalogStatus: 'verified' | 'pending' | 'archived';
  countSupport: 'exact-encoding' | 'reference' | 'estimated' | 'unsupported';
  costSupport: 'complete' | 'partial' | 'unavailable';
  recommendationSupport: 'evaluated' | 'rule' | 'information-only';
  tokenizerRef: string | null;
  contextWindow: number | null;
  maxOutput: number | null;
  reasoningModes: string[];   // 厂商真实枚举，不能给所有模型强套 low/high
  reasoningBudgetSemantics: 'shared-output' | 'separate' | 'unknown';
  capabilities: string[];
  evidenceLevel: 'official-capability' | 'local-evaluation' | 'unverified';
  priceRef: string | null;
  sources: { url: string; checkedAt: string; claim: string }[];
};
```

PriceSpec 记录：id、modelId、currency、原始计价单位、标准化每百万价格（十进制字符串）、cacheHit/cacheWrite 价格、reasoningBillingMode、reasoning 单价、地区/服务档位、tier 选择规则、生效日期、checkedAt、sourceUrl。

推理计费模式限定为 `included-in-output` / `separate-rate` / `not-billed` / `unknown`。使用未知模式时禁止报告完整总价。

TokenizerSpec 记录：编码名、资产 revision、sha256、文件路径、许可证来源、已验证模型列表、fixture 版本。Price 与 Tokenizer 更新互相独立，不能因为价格刚复核就把分词器标为刚验证。

目录发布校验：唯一 ID、非负价格、合法币种、mode 引用存在、tier 无空洞或冲突、外链为 HTTPS、过期模型不默认推荐、未核验记录不能成为首选。原子发布 catalogVersion + priceVersion + ruleVersion，避免混版本。

价格时效：7 天提示复核，30 天退出默认排名；是产品策略而非厂商规则。汇率记录方向（例如 USD→CNY）、日期、来源；超过 7 天标记陈旧。缺失汇率时按原币显示，不声称跨币种最低价。

OpenAI 模型名、网页产品名及 API ID 分开。不能仅根据 GPT 版本数字推断成本、tokenizer、可用性或能力。提供方报价来源以[OpenAI 模型文档](https://developers.openai.com/api/docs/models)、[DeepSeek 官方文档](https://api-docs.deepseek.com/)、[百炼价格](https://help.aliyun.com/zh/model-studio/model-pricing)为起点，录入时保存具体条目证据。

补充官方目录入口：[Claude](https://platform.claude.com/docs/en/models/overview)、[Gemini](https://ai.google.dev/gemini-api/docs/models)、[Grok](https://docs.x.ai/developers/models)、[Mistral](https://docs.mistral.ai/models)。其余厂商按需求清单逐家建立来源；不得把聚合商昵称直接视为厂商正式型号。

### 6.1 全量目录与覆盖台账

- 模型身份分为 manufacturer → family → canonical model/version → offering（渠道/地域/访问方式）。推理模式为配置维度，不虚增独立型号数。
- `coverage.json` 保存每个发现项的来源、发现与核验日期、分类依据、canonicalModelId、included/excluded/pending、缺失字段与排除理由。生成覆盖报告时，pending 不能算作核验完成。
- 无公开价格、无 tokenizer、申请制或网页专属也可建目录项；相应功能置 unavailable/unsupported，不能因此过滤掉整个型号。
- 全量目录不等于每次把所有分词器加载到浏览器。服务端只渲染当前分页；加载选中的最多 6 个对比项及其编码。第一版目录筛选用版本化 JSON 的服务端内存索引即可，不必因此新增数据库。
- 对比结果的价格完整性、tokenizer 核验、访问限制分别过滤；网页专属模型不参与 API 总费用排名。未知档位不强行映射 low/high。
- 首发目录核对及每周维护产生差异报告，由维护者核验后发布；新模型发现到录入目标 2 个工作日。暂不自动抓取未核验价格，也不创建无人值守发布。
- 覆盖报告同时列出独立型号数、渠道数、精确编码支持数、可算价数、可推荐数，禁止只报一个“支持模型总数”。

## 7. 成本计算（R03、R04）

### 7.1 输入定义

- I：全部已知输入 token，包含正文和用户手动补充量。
- H：其中缓存命中的 token，必须 `0 ≤ H ≤ I`。默认 H=0。
- V：可见回答 token 情景。
- R：计费推理 token 情景；不能推断的保留 null。
- Pin、Phit、Pout、Pr：对应每百万 token 单价。

在推理按输出单价计费、无其他费用且已确定价格阶梯时：

```text
C = ((I - H) × Pin + H × Phit + (V + R) × Pout) / 1,000,000
```

若推理单独计价，则输出部分改为 `V × Pout + R × Pr`。显式缓存写入/存储等特殊费用另按厂商计费维度处理；首版没有适配的方案标为“不支持完整费用计算”，不能直接忽略。

实际 usage 中 `output_tokens` 可能已经包含 reasoning_tokens。P1 导入前由提供方 adapter 规范化成 V/R，不能将 API output_tokens 再加一次 reasoning_tokens。见[OpenAI 推理说明](https://developers.openai.com/api/docs/guides/reasoning)。

### 7.2 预算情景与区间

P0 三组可编辑的可见回答默认情景（单位 token；纯产品默认值，不是测量结果）：

- 简短：低 128 / 典型 256 / 高 512。
- 标准：低 512 / 典型 1024 / 高 2048。
- 详细：低 2048 / 典型 4096 / 高 8192。

推理预算独立设置，选择 low/high 不自动套一个倍率。明确无计费推理的方案为 R=0；其他方案初始 R=null，提示填写推理预算。只有经核验的模式预算定义或经校准的情景配置才可预填 R。这样保留诚实的不完整预算，而不是制造精确预测。

每组情景分别计算阶梯和费用，展示低/典型/高。“范围”只覆盖这些假设，并不是置信区间或实际费用上限。翻译、摘要等比例关系只能作为可编辑提示，后续有数据再转成预测模型。

上下文阶梯必须读取厂商规则：有的按整个请求套新单价，有的按分段量计费，不能统一当作超出部分加价。严格定义 `>` 和 `≥` 的边界及判断输入量是否含缓存。

金额使用 decimal.js；内部保留十进制精度，展示阶段舍入。微小正值显示 `< ¥0.0001` 等提示而非 ¥0。月度费用为同一情景单次费用 × 请求次数，明确不含增长、变化的缓存及工具调用。

### 7.3 演算验收样例

以下为**虚构测试单价**，不可写入生产模型目录：Pin=2、Phit=0.5、Pout=8，单位为 CNY / 百万 token。

- I=1000、H=0、V=500、R=0 → 0.006 元。
- I=1000、H=200、V=500、R=1000 → 0.0137 元。
- 上述第二个情景重复 1000 次 → 13.7 元。
- 归一化 usage：output_tokens=1500、reasoning_tokens=1000 → V=500，结果仍为 0.0137 元，不得再按 2500 输出 token 计费。
- R=null → total=null，保留已知输入费用和不含推理的部分预算。
- H>I、负单价、缺币种 → 校验失败，不返回正常总价。
- 虚构阶梯以 I>1000 切换：I=1000 用低档、I=1001 用高档；预期值在单测 fixture 中显式写出。
- 汇率测试仅用固定测试汇率 1 USD=7 CNY；不可冒充实时汇率。

## 8. 推荐与预测实现（R05）

### 8.1 P0 规则建议

输入：文本特征、用户可改的 taskType、偏好、候选模型、预算、输出要求、是否需要推理、目录版本。

分类先用确定性规则：长度、代码块、翻译/摘要/抽取等明确指令、多步约束信号。任务分类可以多标签；冲突时标为 other 并让用户选择。用户选择覆盖自动分类。文本长度不等于难度，规则不输出“难度 92 分”。

推荐按以下顺序，使用版本化 rules.json：

1. 过滤不可用、能力不匹配、超限、模式无效的方案。
2. 价格缺失/过期、推理费用未知的方案保留在比较区，但不参与“最低完整预算”排序。
3. 用人工定义并附依据的任务适配档位 `preferred / acceptable / unknown` 分组；未测试时只作为能力启发，不称为实测质量。
4. 省钱：在达到任务基本要求且预算完整的方案里按典型情景费用排序。
5. 均衡：先选 preferred 组，组内按典型费用；证据不足时并列给两个候选。
6. 质量：先按该任务的实测证据排序；没有实测则仅给规则候选，说明“尚无足够实测数据判断质量最优”。
7. 最多返回一个首选和两个备选；使用稳定 tie-break（证据等级、费用、id），保证同版本可复现。

返回 `recommendationKind:'rule'`、reasonCodes、appliedConstraints、excludedReasons、versions。禁止伪造质量百分比；不可把厂商旗舰定位直接当作跨任务质量分数。用户填写的私人价格只影响带标记的本次比较。

### 8.2 P1 真实统计预测

为每个 model × mode × task 类别采集授权的测试 usage，记录输入长度区间、可见输出、推理 token、任务成功与否、重试、价格日期。使用公开/自建测试文本，用户正文不默认入库。

初期用同类任务分位数或简单回归；不需要训练大型模型。数据按任务切分训练/验证，避免同题变体泄漏。每个类别参考至少 50 个样本后评估，样本数不是准确性保证；不足就保留规则/预算情景。

验证包含中位绝对误差、区间覆盖率、区间宽度，以及推荐后的任务通过率/总成本。只有经过留出集校准的区间才能标“历史预测区间”；模型版本或模式变化后重新校准。

云端分类只帮助确定任务特征；其输出不能直接变成 token 预测事实。调用成本单列并设置额度、超时、幂等控制；不每次调用所有候选模型。

## 9. 接口和数据契约

### 9.1 P0 服务端接口

- `GET /api/v1/catalog`：支持 q、manufacturer、tier、accessType、countSupport、costSupport、page/pageSize 筛选；默认每页 20、最多 100，返回当前页、total、版本与核验日期。q 限 200 字符，仅用于模型名/ID 搜索，不放入用户提示词；无结果返回空集合，非法参数 400，正常 200/304，目录不可用 503。ETag 与缓存键包含版本和规范化查询参数。
- `GET /api/v1/catalog/[id]`：返回单个条目的能力、价格、来源和支持状态，未知 ID 返回 404；前台按选中项加载详细数据。
- `GET /api/health/live`：仅表明进程存活。
- `GET /api/health/ready`：检查目录 schema、必要资产与版本可读，异常 503；不暴露路径/密钥。

P0 没有 `POST /estimate` 或 `POST /recommend`：这些函数直接在浏览器执行，减少正文外传与服务端成本。

### 9.2 浏览器计算契约

```ts
type EstimateRequest = {
  modelIds: string[];           // 单次对比 1～6 个，模型库总量不限
  inputCounts: Record<string, CountResult>;
  extraInputTokens: number;      // 默认 0，手动补充
  visibleBudget: { low: number; typical: number; high: number };
  reasoningBudget: Record<string,
    { low: number; typical: number; high: number } | null>;
  modeByModel: Record<string, string>;
  cacheHitRatio: string;         // 十进制 [0,1]，默认 "0"
  monthlyRequests: number;       // 整数 ≥ 1
  preference: 'cost' | 'balanced' | 'quality';
  taskType: string;
  catalogVersion: string;
};
```

估算输入范围按 low/typical/high 各自参与成本计算；若计数只有上下界，用声明的中点作为典型情景并标注，不把它当真实计数。计算返回 `complete / partial / unavailable`，金额字符串、原币、换算依据、情景、排除原因、版本和 source refs。

错误码至少包含 `INPUT_TOO_LARGE`、`TOKENIZER_UNAVAILABLE`、`UNKNOWN_MODEL`、`INVALID_BUDGET`、`UNSUPPORTED_MODE`、`CONTEXT_EXCEEDED`、`PRICE_STALE`、`PRICE_UNAVAILABLE`。用户看到中文解释，开发日志只记录码和耗时。

### 9.3 后续接口预留

P1 的 `POST /api/v1/analyze` 和 `POST /api/v1/count-official` 默认关闭。启用时采用服务端密钥、明确正文上传提示、请求体限制、速率与日预算限制、超时、usage 记录与不含正文的审计。服务端只允许预配置提供方地址，不能成为任意 URL 代理。

若使用 OpenAI 官方计数，可参考[输入计数接口说明](https://developers.openai.com/api/docs/guides/token-counting)。接口访问能力、地域和账号权限在实施时核验；P0 不依赖它。

## 10. 安全、隐私与导出（R07、R09）

- 输入、文件内容、撤销缓冲仅保留在页面内存；LocalStorage 只存非敏感偏好。
- 不把正文写进 URL、SSR props、异常追踪、日志、统计事件或分享链接；没有默认历史正文缓存。
- 浏览器解析 JSON/CSV，不执行输入；CSV 单元格以 `= + - @` 等开头时防公式注入。
- 来源链接由受信目录维护，限制协议；用户文本按文本节点渲染，不使用危险 HTML 注入。
- 设置匹配 Next.js 的 CSP（上线时验证 nonce/脚本策略）、内容类型防嗅探、Referrer Policy。CSP 不能阻止 Worker 后再偷偷关闭保护。
- 无第三方远程字体、会话回放；P0 不保存 API Key。
- 导出默认排除原文，包含所有计算假设与数据版本。导出文件是用户主动下载，不上传到服务器。

## 11. 阿里云 ECS 部署方案（R11、R12）

### 11.1 拓扑

域名 A/AAAA → ECS 公网入口 80/443 → 宿主机 Nginx → `127.0.0.1:3000` → Next.js 容器。初版一个应用容器、无数据库。现有服务器若已有网站，以独立 vhost/端口部署，避免覆盖原配置。

用户现有 ECS 信息未知，不假设已有 Docker、不改 DNS、不发起实际部署。本节是实施步骤。

### 11.2 构建产物

`next.config.ts` 使用 `output: 'standalone'`。多阶段构建安装锁定依赖、运行测试与 `next build`，运行镜像复制 `.next/standalone`、`.next/static` 和 `public`，以非 root 用户执行 `node server.js`。standalone 不会自动把所有静态资源都复制进去，见[官方 output 文档](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)。

镜像内监听 `HOSTNAME=0.0.0.0`、`PORT=3000`；compose 只映射 `127.0.0.1:3000:3000` 到宿主机。按 ECS 架构构建 Linux 镜像，不能直接搬 macOS node_modules。用 `restart: unless-stopped` 和健康检查，不叠加 PM2。

配置键：`SITE_URL`、`SITE_NAME`、`ICP_NUMBER`、`CONTACT_EMAIL`、`CATALOG_VERSION`、`ENABLE_CLOUD_ANALYSIS=false`、`LOG_LEVEL`。公开值允许渲染；未来 API 密钥仅服务端环境变量，禁止 `NEXT_PUBLIC_` 前缀。SSR 中读取公开运行时配置以避免换域名必须改业务代码。

### 11.3 发布顺序

1. 核对 ECS 系统/资源/架构/地域、已有进程、端口、安全组、域名与备案信息；不重复采购。
2. 在开发机或 CI 的匹配 Linux 架构环境构建，测试后给镜像打 commit 标签；记录目录版本与资产 hash。
3. 经可用的镜像仓库或受控文件方式传入 ECS，启动到备用本地端口并健康检查。
4. 先备份现有 Nginx 配置，再创建域名对应 vhost，代理到容器；运行 `nginx -t` 后 reload。
5. 安装匹配域名的 HTTPS 证书，配置自动续期和到期告警；HTTP 重定向 HTTPS。
6. 安全组开放业务所需 80/443；SSH 仅授权来源；应用端口不公网开放。
7. 配置 DNS 后验证解析、HTTPS、首页 SSR、模型目录、静态资产、计算与导出。
8. 核对真实备案号及链接、隐私联系方式、数据日期，再发布正式入口。

已有备案域名不意味着本机 DNS、证书或备案接入信息已经配置好；按实际服务状态核对，不在文档中假定完成。

Nginx 负责 TLS、基本请求限制与代理；保留 Next.js 所需请求头和 RSC 行为，不自行给所有响应加统一长缓存。如使用流式 SSR，关闭该代理位置的响应缓冲；参见[官方自托管指南](https://nextjs.org/docs/app/guides/self-hosting)。

### 11.4 运维、回滚和扩容

- 监控：进程健康、HTTP 5xx、SSR 延迟、CPU/内存、磁盘、证书有效期；日志不含用户正文。
- 日志轮转防止磁盘耗尽；保留最近两版镜像、目录和部署配置。
- 更新：备用端口启动 → readiness → 验证 → Nginx 切换 → 保留旧容器短期回滚。
- 回滚：切回上一端口/镜像与配套目录；清理或版本化受影响公共资源缓存；验证 SSR 与计算。
- 备份：源代码、目录快照、部署配置；密钥和证书按现有安全存储方式管理，不提交仓库。
- 有持续瓶颈后再增加第二应用实例、共享目录分发或 OSS/CDN；首版不引入 Kubernetes、RDS 或 Redis。
- 费用由已有 ECS、带宽、证书方案和可选存储决定；无型号信息不报固定月成本。P0 没有推理 API 成本，但不是零运营成本。

### 12.2 集成与 E2E

- 粘贴 → 切换模型 → 修改预算 → 推荐 → 复制/导出全流程。
- 快速连续输入验证只显示最新结果；加载失败、取消 Worker、存储禁用可恢复。

### 12.3 性能验证

首屏指标与大文本目标见需求 R10；报告须写设备、网络、浏览器、是否冷缓存。分词资源不进入首屏同步包；小文本常见操作在交互线程上没有可感知卡顿。1 MiB 超时允许取消且不泄漏内存。

上线门槛：关键路径通过、目录真实且有效、无重复计费、无正文外传、生产 SSR 可验证、HTTPS 可用、备案和联系方式真实、回滚已演练。任何一项未通过，TODO 保持未完成。
